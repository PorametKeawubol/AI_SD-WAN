# ผลการทำนาย packet loss และการตรวจการทำงานผ่าน flexiEdge

โมเดลรุ่นทดลองลด MAE ของ packet loss จาก Persistence ได้ **31.4%** ใน Holdout ของเครือข่าย Linux veth/NetEm ที่ส่งแพ็กเก็ตจริง ผลนี้ยืนยันความสามารถภายในชุดทดลองดังกล่าว ส่วนการลดเวลาที่บริการผิด SLA ผ่าน flexiEdge ต้องพิจารณาผลทดลองปลายทางแยกกัน ห้ามใช้ตัวเลข 31.4% แทนอัตราผ่าน SLA หรืออัตราความแม่นยำทั่วไป

เอกสารนี้ต่อจาก [ผลการปรับโมเดลระดับลิงก์เดิม](FORECAST_SEARCH_20261017.md) โดยแก้ข้อจำกัดที่ Holdout loss เดิมเป็นศูนย์ทั้งหมด เก็บข้อมูลและบันทึกวิธีไว้ใน `reports/loss-confirmation-20261018` และตรวจการทำงานผ่าน flexiEdge แยกใน `reports/flexiedge-candidate-validation-20261018`

## โมเดลและวิธีเลือก

ชุดโมเดลมีหัวทำนายสี่ตัว ได้แก่ RTT ใช้ Ridge, jitter ใช้ XGBoost, packet loss ใช้ Ridge และ utilization ใช้ XGBoost การทดลองนี้เปลี่ยนเฉพาะหัว loss ส่วนอีกสามหัวเหมือนรุ่นก่อนทุกค่า

ใช้ข้อมูล 18 episodes แบ่งตามลำดับเป็น Train/Tune/Acceptance/Holdout จำนวน 9/3/3/3 รอบ แยกทั้ง episode ระหว่างชุด ไม่สุ่มแถวจากรอบเดียวกันไปอยู่คนละชุด ใช้ประวัติ 12 จุด ห่างประมาณ 5 วินาที เพื่อคาดการณ์อีก 30 วินาที

ก่อนเปิด Tune/Acceptance/Holdout ตรวจพบว่าแผนแรกไม่มีประวัติภาวะปกติครบสำหรับฝึก จึงบันทึกการแก้แผนล่วงหน้า เพิ่มสามรอบปกติใน Train และเก็บ Tune/Acceptance/Holdout ใหม่ทั้งหมด พร้อมสลับรูปแบบ ramp/step/burst ระหว่าง WAN เก็บแผนเดิม รอบเกินหนึ่งรอบ และรอบที่หยุดกลางทางไว้ ไม่ใช้เป็นผลยืนยัน

ค้นหา Ridge และ XGBoost ตามแผนที่กำหนดก่อนเริ่ม ใช้ Tune เลือกพารามิเตอร์และน้ำหนัก residual จาก 0/.25/.5/.75/1 ผลเลือก Ridge alpha=0.1 และน้ำหนัก 0.75 ผ่าน Acceptance ด้วย MAE 4.455 เทียบ Persistence 5.841 จุดเปอร์เซ็นต์ จาก 69 หน้าต่างในสามรอบ ตรึงผลเลือกก่อนเปิด Holdout และไม่เลือกหรือฝึกใหม่ตามผล Holdout หรือผล flexiEdge

## ผล Holdout ที่มีการสูญเสียจริง

| ช่วงที่ใช้ประเมิน | จำนวนหน้าต่าง | Persistence MAE | รุ่นเดิม v2 MAE | รุ่น loss ใหม่ MAE |
|---|---:|---:|---:|---:|
| ทุกหน้าต่าง | 63 | 4.667 | 5.610 | 3.202 |
| ค่าจริง loss มากกว่า 0% | 41 | 4.976 | 8.586 | 3.906 |
| ค่าจริง loss เท่ากับ 0% | 22 | 4.091 | 0.065 | 1.890 |

หน่วย MAE เป็นจุดเปอร์เซ็นต์ ค่าต่ำดีกว่า คำนวณการลด MAE เป็น `100 × (1 − MAE ใหม่ / MAE Persistence)` ทุกวิธีใช้หน้าต่างและค่าเป้าหมายเดียวกัน รุ่นใหม่ลด MAE รวม 31.4% และลดประมาณ 21.5% เฉพาะหน้าต่างที่มีการสูญเสียจริง ส่วนช่วงค่าจริงเป็นศูนย์รุ่น v2 ยังดีกว่ารุ่นใหม่ จึงไม่กล่าวว่ารุ่นใหม่ชนะทุกเงื่อนไข

ผลต่าง absolute error ของรุ่นใหม่ลบ Persistence มี episode-block bootstrap 95% CI เท่ากับ −1.992 ถึง −0.975 จุดเปอร์เซ็นต์ ใช้เพื่ออธิบายชุดนี้ซึ่งมี Holdout อิสระเพียงสามรอบ ไม่ใช้เป็นการรับรองกับเครือข่ายทุกประเภท

การตรวจเกณฑ์ค่าจริง loss >1% ได้ TP/FP/FN เท่ากับ 40/7/1 สำหรับรุ่นใหม่ และ 38/7/3 สำหรับ Persistence โดยไม่ใช้ผลนี้ปรับ threshold หรือเลือกโมเดลใหม่ ค่า recall 97.6% ไม่ใช่ accuracy ของโมเดลทั้งระบบ

## หลักฐานและขอบเขต

ส่ง ICMP จริง 135,000 packets และได้รับ 128,310 packets ใน 1,350 batches ตรวจ RTT/jitter/loss จาก stdout และตรวจ utilization กลับจากตัวนับ TX ดิบครบทุก batch คลาดเคลื่อนจากค่าที่บันทึกสูงสุดเป็นศูนย์ จับ PCAP เฉพาะ 1,000 frames แรกต่อ WAN ในแต่ละ campaign ไม่ใช่ทุกแพ็กเก็ต

ข้อมูลระดับลิงก์ใช้ veth/NetEm บนเครื่องเดียว ไม่มี flexiEdge, VPP, overlay หรือวงจร ISP อยู่ในเส้นทาง utilization คำนวณจาก TX ของ veth ส่วน telemetry ที่ใช้งานจริงอ่านตัวนับ VPP ดังนั้นผล RTT/jitter/utilization ที่ลด MAE 78.3/74.9/76.2% เป็นผลจากชุดเดิม 69 หน้าต่าง ไม่ใช่ผลจากชุด loss 63 หน้าต่าง และไม่ใช่การยืนยันการถ่ายโอนโมเดลไปยัง flexiEdge

ชุด loss นี้เน้นการเปลี่ยน loss ขณะที่ RTT และ utilization เปลี่ยนน้อย หัวเดิมที่ไม่ได้ปรับจึงอาจแย่กว่า Persistence ในชุดนี้ ผลทุกตัวชี้วัดยังอยู่ใน `confirmation.json` โดยไม่ตัดผลที่ไม่ดีออก

## การทำงานจริงผ่าน flexiEdge

KVM ยังเปิดไม่ได้ จึงใช้ QEMU TCG ชั่วคราวกับ flexiEdge สองเครื่อง เครื่องละ 4 vCPU และ RAM 4 GB ข้อมูลผ่าน flexiManage REST API และ agent RPC บันทึกใน TimescaleDB โหลดโมเดลเดียวกับที่ตรึงไว้โดยระบุ `--model` ชัดเจน ไม่แทนที่โมเดลเริ่มต้นหรือเปิดใช้เป็นระบบควบคุมปกติ

ชื่อ `predictive_synthetic_lab` และ `--experimental-synthetic-forecast` ใน runner เป็นชื่อเดิมของโหมดทดลอง รอบนี้ระบุเส้นทางโมเดลที่ฝึกจากแพ็กเก็ตระดับลิงก์จริงและบันทึก fingerprint ทุกครั้ง ชื่อดังกล่าวไม่ได้หมายความว่าแทน telemetry ปลายทางด้วยข้อมูลจำลอง และไม่เปลี่ยนชื่อหรือโค้ดระหว่างคู่ทดลอง

โปรแกรมตรวจวัดเดิมส่ง ICMP 100 packets ต่อ WAN และอ่าน VPP counters เพิ่มตัวตรวจวัดต่อเนื่องบน edge เพื่อให้ RPC อ่านผลล่าสุดได้เร็วขึ้น โดยรักษาค่าและเวลาที่วัดจริง ไม่เติมศูนย์ ไม่แก้ timestamp ไม่ยอมรับข้อมูลล้าสมัยหรือข้ามเกณฑ์ระยะห่าง 4–6 วินาที

ขั้นคาดการณ์ยังใช้กริดห้าวินาทีตามสัญญาเดิม โดย interpolate เฉพาะระหว่างจุดที่วัดและมาถึงแล้วเท่านั้น การคำนวณกริดนี้เกิดในหน่วยความจำ ไม่แก้ค่าหรือเวลาของ telemetry ดิบ และไม่ข้ามช่วงข้อมูลขาดหายหรือ extrapolate ออกนอกข้อมูลที่มี

| การตรวจ Manual รอบละสามนาที | หน้าต่างประวัติพร้อมคาดการณ์ต่อ WAN | ความหมาย |
|---|---:|---|
| v2 เรียกวัดผ่าน RPC ทีละครั้ง | 1/21 | เวลารอ RPC ทำให้ประวัติขาดช่วง |
| v2 แยกตัวตรวจวัดต่อเนื่อง | 25/25 | ทำงานได้ในรอบภาวะปกตินี้ |
| v3 ภาวะปกติ | 11/24 | โมเดลล่าสุดสร้าง forecast จริงได้ แต่ยังมีข้อมูลขาดช่วง |
| v3 ระหว่างเหตุ loss | 0/19 | ไม่ได้ forecast ที่ผ่านเกณฑ์ประวัติ จึงไม่ถือว่าทำนายเหตุ loss ผ่าน flexiEdge สำเร็จ |

รอบ v3 ภาวะปกติมีเป้าหมายจริงสำหรับวัดความคลาดเคลื่อนแปดหน้าต่างต่อ WAN ค่า RTT MAE ของโมเดลเท่ากับ 25.1/44.3/68.9 ms เทียบ Persistence 1.6/2.1/3.2 ms ตาม WAN1/2/3 จึงยังมีปัญหาการใช้โมเดลในสภาพที่ต่างจากข้อมูลฝึก รอบ Manual ทั้งหมดไม่มีคำสั่งเปลี่ยนนโยบาย และตรวจว่าโมเดลกับนโยบายคงเดิม

## การประเมิน SLA และเกณฑ์ภาพรวม

กำหนดผลต่างสัดส่วนช่วงที่ผิด SLA ของ Predictive ลบ Reactive เป็นตัวชี้วัดหลัก แยกจาก forecast MAE ใช้เหตุการณ์ โหลด และรอบซ้ำเดียวกัน ไม่กล่าวว่า AI ลด SLA violations หากยังไม่มีคู่ทดลองที่วัดได้สมบูรณ์

ผู้จัดทำยอมรับเป้าหมายภาพรวมอย่างน้อย 80% และมุ่งสู่ 90% ของกรณีที่วัดผลได้สมบูรณ์ โดยรายงานกรณีไม่ผ่านและรอบที่วัดผลไม่ได้แยกกัน ผลเดิม Reactive ผ่าน 14/16 กรณี หรือ 87.5% เป็นผลของ Reactive ไม่ใช่ความสำเร็จของโมเดลใหม่ ส่วนเกณฑ์ SLA รายกรณี 98% ยังคงเดิมเพื่อเทียบกับผลเดิมได้

ก่อนเริ่มคู่ทดลองรุ่นใหม่ รอบเตรียม voice สองครั้งได้ SLA 56/60 วินาทีในช่วงปกติ (93.3%) และไม่ผ่านเกณฑ์เดิม 98% รอบ bulk ผ่านภาวะปกติ 60/60 แต่มีช่วงที่โปรแกรมส่งโหลดไม่ถึง 90% จึงใช้เทียบ SLA ไม่ได้ เก็บผลทั้งหมดไว้ ก่อนการเปรียบเทียบได้ประกาศยอมให้ช่วงปกติมี SLA อย่างน้อย 90% เนื่องจากความผันผวนของ TCG โดยไม่เปลี่ยนเกณฑ์ SLA ระหว่างเหตุ 98% เกณฑ์โหลด เวลา หรือความสดของข้อมูล

รอบแรกของแผนหก trials หยุดก่อนส่งแพ็กเก็ต เนื่องจาก journal ของคำสั่งก่อนหน้ายังค้างในสถานะ queued ตรวจพบว่า jobs เสร็จและค่าบนอุปกรณ์ทั้งสองตรงกับ controller จึง reconcile ด้วยการอ่านกลับโดยไม่สั่ง PUT ซ้ำ แล้วลองแผนเดิมอีกครั้ง เก็บความพยายามแรกไว้ครบถ้วน ผลสุดท้ายและสถานะการคืนระบบระบุใน `reports/flexiedge-candidate-validation-20261018/validation.json`

ผลรอบสุดท้ายวัดได้สมบูรณ์ครบหกรอบ เป็นสามคู่ โดยทุกวิธีมีโหลดจริงและ PCAP ผ่านเกณฑ์ความถูกต้องของการวัด แต่ไม่มีรอบใดผ่านเกณฑ์ผลบริการรายกรณีครบทั้งหมด

ช่วงความเชื่อมั่น 95% แบบสุ่มซ้ำรายคู่ของผลต่างช่วงผิด SLA เท่ากับ −40.0 ถึง +5.7 จุดเปอร์เซ็นต์ จึงยังไม่ยืนยันข้อได้เปรียบ แม้ค่าเฉลี่ย Predictive ดีกว่า และมีสองคู่ที่ loss/goodput ปลายทางแย่กว่าเล็กน้อย ผลนี้จำกัดเฉพาะ S12 voice บน TCG ไม่ใช่อัตราผ่านทุกกรณีหรืออัตราความแม่นยำของโมเดล และไม่ใช้ผลนี้ปรับพารามิเตอร์ใหม่
